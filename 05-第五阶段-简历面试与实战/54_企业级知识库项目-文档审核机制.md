分别分块、解析存入向量数据库、全文检索数据库、图数据库。

但我们没有做任何的审核。

发布本身如果缺少门禁，任何草稿都可以直接进索引，对知识库来说风险很大

内容可能带隐私敏感信息、无效垃圾内容等被检索和问答引用。

实际上文档会有 4 种状态：

| 值 | 枚举 | 含义 | 是否进 RAG / 全文 / 图谱 |
| --- | --- | --- | --- |
| 0 | **Draft** 草稿 | 编辑中，仅作者/协作者可见 | 否 |
| 1 | **Published** 已发布 | 正式对外，可被检索与问答 | **是**（发布后异步建索引） |
| 2 | **Archived** 已归档 | 下线保留，历史可查但不再检索 | 否（归档时清索引） |
| 3 | **PendingReview** 待审核 | 已提交发布，等审核员处理 | 否（审核期间不可被搜到） |

只有 Published 会写三套索引

Draft / PendingReview / Archived 状态的文档都不应出现在向量检索、关键词搜索和图谱召回里。

![image](../IMG/2026-08-17_企业级知识库项目：文档审核机制、四种状态流转/1_公众号_Yi昭.webp)

为了方便测试，我们可以加一个环境变量 DOCUMENT\_REQUIRE\_APPROVAL 来控制文档发布是否要审批流程

这样，文档状态流转就需要加几个对应的接口：

- **publish 发布文档**

需要审批的话，文档 → PendingReview 状态，不写索引；

不需要审批，文档 → Published 状态，并投递 MQ 建 RAG / 全文 / 图谱三套索引。

- **submit 提交审批**

与需审批场景下的 publish 效果相同：

文档从 Draft / Published → PendingReview 状态

如果之前是 Published，会先清掉旧索引

- **approve 审核通过**

PendingReview → Published，并投递 MQ 重建三套索引。

- **reject 审核驳回**

PendingReview → Draft，需传驳回意见

不进索引，作者改稿后可再次 publish / submit

- **archive 归档**

仅 Published 可归档 → Archived，异步清理三套索引，正文仍保留。

- **save-draft 保存为草稿（下架编辑）**

Published → Draft，清索引后可改内容，再 publish 或 submit 重新走发布/审核。

## 总结

这节我们完善了文档的 4 个状态：

草稿 Draft、待审核 PendingReview、已发布 Published、已归档 Archived

只有已发布状态的文档才允许进入向量库、全文检索库、图数据库三套 RAG 索引

草稿、待审核、归档文档全部不参与检索召回，避免隐私、垃圾、未审核内容被问答引用。

新增 kh\_document\_review 审核记录表，持久化每一条审批流水，完整留存审批人、审批结果、审批意见、操作时间，支持追溯历史审核记录。

并且加了一些状态流转的接口

publish、approve、reject、archeive 等

这样，文档的全流程就完成了，覆盖文档上传解析、提交审核、审批流转、修改重审、归档下线全生命周期。
